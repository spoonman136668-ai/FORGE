# ACC-G92: self-speculative microtree feasibility preregistration

**Frozen before G92 implementation/measurement. Research-only G91–G106 slate in draft PR #1329.** The source baseline is FORGE `main` SHA `0810ecf3df6378bcbfe5239d30df836b7e12a602`. This is the **GPU bottleneck track's CPU analytical proxy**, distinct from GPT-2 CPU experiments. No pretrained-model, GPU, FP16, or real-throughput claim follows from this screen.

## Hypothesis and nonclaim

Question: If a cheap low-rank **self-sketch** of the same synthetic reference transition network proposes a small tree of next tokens, does the accepted-token yield overcome the number of verification nodes and draft operations? The verifier must exactly reconstruct the reference greedy stream. No external or separately trained draft model is used. The analytic break-even ratio is *not* a measured acceleration, nor proof of feasibility on a real autoregressive transformer.

## Locked controls and data

- NumPy float64 synthetic two-token Markov oracle: vocabulary `64`, reference `A[last] + 0.2*B[penultimate]`, with independent standard-normal dense `A, B` drawn from each of seeds `[9201,9202,9203]`. All logits finite. The oracle next token is `argmax` (first index on tie).
- Draft is the rank-8 truncated SVD approximation of both `A` and `B` computed **once** from the same matrix before trial. It proposes only its own top choices; it must never observe oracle outcomes when constructing branches. Record SVD setup time separately; no model-training claims.
- Start histories: 16 independent ordered pairs, sampled with the same seeded generator *after* `A` and `B`. Each history generates **24 exact greedy tokens** with the reference oracle; no cherry-picked contexts.
- Candidate arms: fixed tree depth `3`; widths `1,2,4`; every tree node (including root) is evaluated by the oracle, while the self-sketch expands all nodes at draft depth 0–2; tree verifier can produce at most 4 exact tokens per verification batch. Use full branching; do not silently approximate verifier work as a single token.
- Deterministic, 3×16×3 = **144 cases**, each 24 generated tokens. At each batch, confirm output matches the entire corresponding reference greedy stream, including a rejected branch's corrective token. Measure: verifier batches, fully verified tree nodes, draft top-choice computations, accepted draft tokens, output tokens; compute amortized nodes/tokens, accepted tokens/batch, and theoretical maximum allowable verifier cost per node under a predeclared draft-cost assumption.
- **Analytic cost control:** single reference greedy step costs `1.0` unit; each draft node expansion costs `0.1` units; each verified tree node costs a hypothetical `v` units. For `1.15x` *required* improvement, `v_max=(24/1.15 -0.1*draft_expansions)/verified_nodes`. This is an **optimistic necessary condition**, not measured GPU throughput. Record `v_max` for every case and medians by width. If `v_max<=0` for any case, that case is infeasible even at free verifier execution. Do not relabel the above assumption as measured hardware. No empirical end-to-end speedup may be reported.
- **Early-screen disposition:** `NO_GO` if any greedy mismatch, missing/infinite counts, or median `v_max<=0` for every width. Otherwise `FEASIBILITY_ONLY`, explicitly **UNVERIFIED** for TinyLlama, GPU and scientific acceptance. Actual promotion requires independent GPU model baseline, real batched verifier implementation, measured full token throughput, exactness, held-out prompts, frozen acceptance criteria, and final platform regression.
- Source/measurement custody: `research/acc_g92/` code and exact JSON observations from GitHub CI (or other permitted qualified runner), using stdout. Publish all cases and environmental versions; do not mix measurements from different commits or overwrite results with reconstructed values. No paid API or novel controller, and no mutation of accepted baselines.

**Status: preregistered hypothesis, no G92 measurement at the time of this commit.** All thresholds/hyperparameters above are frozen for this screen. Any change must use a new version rather than retroactive tuning.
