## Four independently measured arms
1. **PT_manual:** original G68 manual incremental KV decode without cross-request shared-prefix cache.
2. **PT_hf:** original Hugging Face `generate()` model-only library control without shared-prefix reuse.
3. **PT_shared:** original G68 bounded (2 entries, 42,000,000 bytes) exact-prefix cache and per-request KV copy with no future knowledge.
4. **ORT_http:** newly exported authentic ONNX Runtime CPU `ORTModelForCausalLM` served through same localhost HTTP transport and request queue, one shared model/session, no invisible precomputed answer cache. External ONNX execution is the independent backend, but **not** a full optimized serving engine with dynamic batching.

- Keep output parity against the PT_manual reference on all arms/requests, including independent ONNX, on every measured repetition.
- One unmeasured warmup per arm with *separate non-heldout public text*; then **three complete paired counterbalanced order-rotated repetitions per cohort**, every arm running the identical 12 requests. 2 cohorts x 4 arms x 3 repetitions x 12 responses = **288 timed HTTP responses** / 2,304 required output tokens (subject to strict admission).
- Measure *whole HTTP cohort elapsed*, individual client latency/p50/sample-p95, sampled process CPU seconds, sampled worker RSS every 10 ms (explicitly approximate, not exact peak), model allocated/cached tensor bytes, scheduler/queue overhead and source/graph identifiers. Separately measure cold PyTorch load, ONNX conversion/export, ORT session start and warm startup costs; exclude these from warm HTTP ratio but disclose their amortization break-even. Track real wall-clock end-to-end server request intervals, not kernel-only or single-call latency.
- Use identically bounded request-level parallelism: never allow the independent engine more than 3 concurrent active requests or >3 logical CPU slots. No unrestricted worker spawn, paid APIs, 3rd-party endpoint calls, production queues, other project runners or controllers.
