## Engineering hypothesis
The existing R16 agent-free SQLite resource-repair compiler repairs `with sqlite3.connect(...)` inside a temporary-directory scope, preserving transaction commit and rollback and closing handles, but rejects `import sqlite3 as <alias>` with `SQLITE_IMPORT_UNTRUSTED`. An independently sourced, bounded native AST normalization step can safely convert a single SQLite import alias when **every** binding use is a direct `alias.connect(...)` call in a simple `with`, then invoke the unchanged R16 repair compiler. This creates a *functional source-repair candidate* for a new syntactic subfamily without using the original after-source or a model/agent.

Reject any ambiguity. No network, owner/worktree, model or arbitrary subprocess inside the proposer.
- Candidate budget: exactly **one** proposed AST-normalization+R16 repair per permitted source, plus the unchanged R16 baseline and a no-repair control. Source must compile and have changed contents with versioned SHA-256 receipt, separate preimage SHA-256 and no acceptance/RSI permission.
- Development specimens: one ordinary unaliased source to verify parity, two independent alias spellings and real SQLite native subprocess commit/rollback and temporary-directory cleanup (Linux and Windows), plus negative controls for wrong failure class, hash/path drift, shadowing, alias outside controlled with, unexpected import, corrupted source, unchanged source/idempotence.
- Primary engineering outcome: input aliases previously rejected by R16 yield a syntactically valid, resource-safe original-source patch with actual native SQLite transaction and cleanup behavior, **without** regressing any existing R16 tests or protected full suite. On Windows the original unclosed database may fail temporary-dir cleanup; Linux original can appear healthy due filesystem semantics, so the restructured transaction/cleanup tests must still PASS on both platforms.
