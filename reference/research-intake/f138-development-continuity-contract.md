# F138 — sustained development continuity and durable custody

## Authority and baseline

F137's authentic Windows SYSTEM recovery at 2026-10-18T10:07:32Z led to
F136 controller run 39118017343 and development run 39118033321.
Its bounded dispatch and both development OS jobs passed, **but that
single recovery is not sustained-continuity acceptance**.

F138 is **development-only**. The F136 frozen source, F137 recovery
safeguards, operator pause, 96-per-UTC-day cap, main identity, execution
concurrency and protected science admission remain unchanged.
Windows remains a fallback, never a replacement for genuine GitHub cron.
No Codex, paid inference, Cloudflare write, new scheduler/controller,
accepted-reference mutation, optimizer promotion or scientific first-use.

## Missing evidence and this first implementation gate

Existing child F129 receipts authenticate source and OS behavior but
do not identify the **controller run that actually requested the child**.
This change adds `f138-lineage.json` and `f138-lineage.sha256` to each
existing Ubuntu and Windows integrated-cycle worker. The report records
the native GitHub event, workflow origin, parent run ID, source SHA,
run attempt and explicit science-denial fields. F129's already-existing
cross-run proof reads both new artifacts, verifies the SHA256 receipts,
requires identical canonical bytes across platforms and checks source
and run identity against prior F129 reports. No dispatch behavior changes.

A content hash detects byte changes but **does not authenticate GitHub
authorship by itself**. F138 cross-run acceptance must also verify the
actual GitHub run endpoint, branch, attempt, artifact ownership, unexpired
archive digest and verified controller decision. A supplied parent ID
is an asserted value until independently matched to the controller's
provider record and its recorded dispatch. All pre-merge runs lack the
new receipt and cannot qualify for this new proof.

## Sustained operational acceptance (still pending)

Using independent provider reads, retain a rolling sequence covering
at least three **new**, first-attempt, successful integrated development
runs over at least twenty minutes, on one qualified protected source,
including a genuine scheduled cycle and a controller-qualified F137
Windows fallback cycle. Require exact source/parent matching, successful
Ubuntu and Windows jobs and their independent F129/F138 receipts. Verify
start/completion timestamps and absence of simultaneous active execution,
replay, duplicated child-parent mapping, unknown origins, schedule
impersonation, truncated history or exhausted budget. Record legitimate
`SKIP` decisions as negative/guard evidence, never as a successful
dispatch. Genuine scheduled ancestry is never inferred from a relay.

A first-attempt controller `workflow_dispatch` with a successful
decision is evidence of a development-only wake, **not** proof that
Windows stayed up indefinitely or that the integrated workflow was
directly cron-triggered. When authoritative data is insufficient,
return `PENDING` or `QUARANTINED`, not PASS. An unrelated green
pull-request/push run is not operational evidence.

## Durable retention and advancement

The F138 witness archives use GitHub's 90-day Actions artifact retention.
This makes near-term retrieval possible, **not** perpetual custody.
Before concluding F138, reconcile the actual run/decision/artifact IDs
and individual SHA256 digests into a separate append-only,
source-reviewed, versioned, non-secret Git record or independently
controlled durable custodian. Require reviewer-approved promotion of
that record; do not let a scheduled observer self-commit to protected
main. Preserve the raw receipts and every failed gate as negative
evidence. Do not falsely classify a downloaded ZIP hash as a signature.

The first F138 PR establishes exact provenance witnesses and focused
negative tests. A second, separately qualified read-only aggregation
gate must build the rolling multi-run acceptance and durable custody
record; only then can F138 be marked accepted.
